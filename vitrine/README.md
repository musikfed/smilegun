# Стандарт изображений PL Code Store · vitrine/

**Один репозиторий = одна папка vitrine/ = свой источник правды.** PL Code Store не импортирует статические карточки из view_my_prj. Он читает только файлы исходных репозиториев.

## Куда класть скриншоты

В **исходном репозитории проекта**, а не в PLCodeStore:

    repo/
    ├── src/ ...                    # рабочий исходный код не изменяется
    └── vitrine/
        ├── meta.json               # версия, описание, статус, публикация
        ├── README.md               # эта инструкция (опционально)
        ├── screenshots/
        │   ├── main.jpg            # реальный интерфейс — главное изображение
        │   ├── desktop.png         # дополнительный экран
        │   └── settings.webp       # настройки / другой экран
        └── generated/
            └── cover.svg           # честная дизайнерская обложка/схема, fallback

Выгружать PNG/JPG/WEBP до **3 МБ на файл**, рекомендуемая ширина 1200–1920 px. Допустим SVG, только если это действительно векторный макет, а не выдуманный «скриншот». Файлы **не содержат** токенов, паролей, адресов/телефонов, тайных данных и персональных элементов интерфейса. EXIF лучше удалить.

В meta.json ссылка **относительно корня репозитория**:

    "screenshots": [
      "vitrine/screenshots/main.jpg",
      "vitrine/screenshots/desktop.png"
    ]

**Первое изображение — главное**. Все дополнительные идут в галерею проекта. Витрина берёт URL из соответствующей ветки исходного Git-репозитория и не хранит в себе эти изображения. У разных версий могут быть свои снимки.

## Как автогенерация находит картинки

1. Сначала уже существующие **vitrine/screenshots/** — ручная работа автора не перезаписывается.
2. Затем реальные растровые изображения в исходниках: docs/screenshots, docs/media, screenshots, images, static, assets, **а также в корне**, если название похоже на скриншот интерфейса (Studio, desktop, screen, screenshot и т. п.).
3. Если в момент предложения vitrine ещё нет, Discover копирует **до трёх** проверяемых PNG/JPG/WEBP **в исходный репозиторий, ветку PR**. После Merge они появляются в main. Сам исходный код проекта не изменяется.
4. У проекта с доступной самостоятельной статической HTML-оболочкой Playwright может сделать **реальный браузерный снимок HTML/CSS/JS** и положить его в vitrine/screenshots/desktop.png в ветке предложения. Это не доказательство работоспособности сервера, прошивки или операционной системы на реальном железе.
5. Когда реальных изображений нет, используется **помеченная схема/обложка**, а не фальшивый снимок работающего продукта.

Пока автор не объединил PR с vitrine/ или не дал другое явное разрешение, публичный магазин не показывает проект. Статическая Review Studio выводит открытые предложения только публичных репозиториев.

## Что делать вручную в GitHub

Откройте **свой проект** → **Code** → ветка предложения **plcodestore/vitrine-proposal** → **Add file → Upload files**, путь назначения **vitrine/screenshots/**, загрузите реальные файлы. Затем **Edit** \`vitrine/meta.json\` → измените массив \`screenshots\` (в начале основное фото) → **Commit** в ту же ветку предложения. Обновите Review Studio после очередного Pages build. Если изображения уже есть в main, при следующей подготовке предложения скрипт подберёт их автоматически.

**Два примера:**
- ESP32 MultiBoard Studio: исходный файл \`Studio esp32_2.jpg\` автоматически копируется в \`vitrine/screenshots/main.jpg\` без изменений.
- Ирина Байкал: источник \`ui/web/index.html\` позволяет получить скриншот настоящей HTML-оболочки, но опубликованные фотографии аппаратного запуска требуют отдельного разрешения автора и наличия исходных фото.

## Закрытый проект

Не копируйте приватный код или изображение на публичную витрину. Для закрытого репозитория PL Code Store генерирует **публичную фирменную графическую обложку** без исходников и показывает только явно согласованную версию, если установлены соответствующие флаги публикации. Обработка приватного проекта остаётся в его закрытом PR.

## Переносимость

Папка vitrine/ и относительные пути совместимы с GitHub, GitLab и Forgejo. Адаптеры GitLab/Forgejo должны читать тот же JSON и файлы из исходного репозитория — без привязки формата к GitHub.
